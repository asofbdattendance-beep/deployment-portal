## SQL migrations (run in order in Supabase)

1. `sql/portal_setup.sql` — base tables, RLS, helpers. Schedules/deployments use the **final (v2+) shapes** so a fresh install is correct from the start.
2. `sql/v2_deployment_redesign.sql` — deadline design, restriction rules, `chair_pass`, `prev_year_deployments`, triggers, RLS. **Non-destructive; safe to re-run** — also repairs DBs created from an older `portal_setup.sql` (adds `name`/`status`/`department_id` columns, swaps the old status CHECK).
3. `sql/v3_data_safety.sql` — unique schedule-name index + `audit_log` table (with correct super_admin insert policy).
4. `sql/v4_vss.sql`, `sql/v5_vss_creation.sql`, `sql/v6_vss_roster.sql` — VSS tables, registration, rosters.
5. `sql/v7_consent_matrix_rpc.sql` — consent-matrix RPC for the dashboard.
6. `sql/v8_deployed_department.sql` — `deployments.deployed_department_id` (final dept set by ASO/super_admin late), admin exemption in `block_after_deadline`/`check_deployment`, RLS for aso/super_admin write. **Non-destructive; safe to re-run.**
7. `sql/v9_production_hardening.sql` — **restores** the master-switch + full VSS eligibility checks in `block_after_deadline`/`check_deployment` (regression from v8, which dropped them), blocks centre roles from writing `deployed_department_id`, scopes `vss_sewadars` reads to the caller's subtree (PII), prevents centre roles from modifying `assigned` registrations, restricts `vss-photos` storage to `reg/` + owner/admin, adds a `sewadars` read policy, indexes `deployments(schedule_id, department_id)`, unique-Aadhar index (created only if no dupes), and an `updated_at` trigger on `portal_users`. **Non-destructive; safe to re-run.**
8. `sql/v10_oe_escorts_fixed_days.sql` — **fixes the OE ESCORTS rule mismatch**: sets `min_days`/`vss_min_days = 3` for every OE ESCORTS department (they previously kept the v2 default of 5, so `check_deployment` rejected the app-enforced 3-day writes with *"must have at least 5 consent days"*), backfills existing consents for OE ESCORTS requested/final rows to 3 days, adds a guard trigger on `deployment_departments` (`trg_guard_oe_escorts_min_days`) forcing 3 days for any OE ESCORTS dept created/renamed later, and a BEFORE trigger on `deployments` (`trg_a_clamp_oe_escorts_days`, named to run before `trg_check_deployment`) that forces the matching consent to 3 days at write time. **Non-destructive; safe to re-run.**
9. `sql/v11_schema_consistency.sql` — **repairs a drifted production schema** (where `sewadar_consents` / `deployments` / `centre_allocations` pre-existed, so v2's `CREATE TABLE IF NOT EXISTS` silently skipped the inline UNIQUE constraints and CASCADE FKs): adds the missing `UNIQUE (schedule_id, centre, badge_number)` (and `(schedule_id, department_id, centre)`) constraints that the app's `onConflict` upserts require — deduping first (oldest row per key) and **skipping if a unique index on the exact columns already exists** (a second one would break `ON CONFLICT` inference) — rebuilds the six schedule/dept FKs with the intended `ON DELETE CASCADE` / `SET NULL` actions (single-DELETE schedule/dept cleanup relies on these), and adds the missing supporting indexes. **Non-destructive; safe to re-run.** Verification queries at the bottom of the file.
10. `sql/v12_department_incharges.sql` — **department incharges**: each CENTRE nominates **one incharge per allocated department** (`department_incharges` table, `UNIQUE (schedule_id, centre, department_id)`). Centre roles pick from sewadars of their subtree who consented AND were assigned (requested) to that department — enforced by a guard trigger (`trg_check_incharge`); the incharge must be a consented sewadar deployed to that department and the schedule must still be open. RLS: read for aso/super_admin + same-CENTRE users, write for centre roles on their own CENTRE's departments. **Non-destructive; safe to re-run.**
11. `sql/v13_centre_deployment_lock.sql` — **centre deployment lock**: a CENTRE can **lock deployment** on the Consent & Deploy page — locking is **compulsorily blocked until every allocated department that has deployed regular sewadars has an incharge** (DB-enforced by `trg_check_centre_lock`; the UI lists exactly which departments are missing). While locked, centre-role writes to `sewadar_consents` / `deployments` / `department_incharges` are rejected (regular **and** VSS) by `is_centre_locked` checks added to `block_after_deadline`, `check_deployment`, `check_deployment_batch` and `check_department_incharge`. Only **aso/super_admin can unlock** (DELETE via the Consent Dashboard's "Locked deployments" strip). **Non-destructive; safe to re-run.**
12. `sql/v14_aso_finalize_insert_delete.sql` — **ASO/super_admin full deployment lifecycle on Finalize Deployment**: v8 widened `deploy_v2_update` + `consent_write` for `aso`, but the v2-era `deploy_v2_insert`/`deploy_v2_delete` policies still excluded `aso`, so finalizers could not **assign an awaiting sewadar** (consented, no deployment row yet — needs an INSERT) or **remove a deployment when consent flips to No** (needs a DELETE). This migration widens both policies to `aso` + `super_admin` (centre roles unchanged); the v13 centre-lock delete trigger already exempts admins. **Non-destructive; safe to re-run.**
13. `sql/prev_year_deployments_data.sql` — loads 2415 prev-year badge rows (plain INSERT — run ONCE after the tables exist, do not re-run; PK conflicts on a second run).
14. `sql/v15_protect_finalized_deployments.sql` — **protects ASO-finalized deployments**: a BEFORE DELETE trigger (`trg_block_finalized_delete_deploy`) stops centre roles from deleting any deployment row with `deployed_department_id` set — a centre clearing a department request (or flipping consent to No) on a sewadar the ASO already finalized used to DELETE the whole row, silently destroying the ASO's final decision. aso/super_admin are exempt. The centre pages (Consent & Deploy + VSS) now load the finalized flag: those rows are locked (consent/dept/bhati/chair controls disabled, a `FINAL` pill shown, bulk actions skip them) and `toRemove` never deletes them. **Non-destructive; safe to re-run.**
15. `sql/v16_hardening.sql` — **hardening** (from the security/QA review): **H1** drops the surviving v1 RLS policies (`sched_write`/`dept_depts_write` — which still granted `aso` FULL write on schedules/departments since Postgres ORs permissive policies — plus the obsolete v1 `deploy_*` policies) leaving only the v2+ subtree-scoped policies; **H2** drops the unused owner-owned views `vw_my_centre_sewadars` / `vw_all_deployments` (view-owner = bypassrls → any authenticated user could read ALL sewadars/deployments through them); **H3** flips the `vss-photos` bucket to **private** and scopes the storage read policy to owner / aso/super_admin / the registration's centre subtree (photos are PII; the app now stores the bare `reg/...` path and renders via signed URLs — `vssPhotoUrl` in `src/lib/supabase.js`, `VssPhoto` in `AddVssForm`); v37 adds the `vss_operator` arm to `vss-photos` read + delete; **H4** re-runs the OE ESCORTS consent backfill with `trg_block_after_deadline` disabled (running the SQL editor yields no portal role, so v10's backfill aborts on any done/past-deadline schedule); **M5** adds DB backstops so centre roles cannot flip consent (or edit/delete the consent row, or re-request a different department) on an ASO-finalized sewadar — `trg_block_finalized_consent` on `sewadar_consents` + `trg_block_finalized_deploy_edit` on `deployments`; **M4** rejects phantom-badge deployments (`trg_require_sewadar_exists` — badge must exist in `sewadars` or `vss_sewadars`); **M6** restricts `centre_locks` INSERT to a root-centre user locking their OWN centre (an SC_SP user could previously lock the whole CENTRE); **G+** repairs `audit_log` policies — production carried a v3-era `audit_log_insert` that checked the raw JWT `role` claim (never matches — Supabase tokens say `authenticated`), so super_admin could never write audit rows; now uses `get_portal_user_role()`, and `audit_log_select` is scoped to aso/super_admin instead of all authenticated users. **Non-destructive; safe to re-run.** Verification queries at the bottom of the file.
16. `sql/v17_rules_audit.sql` — **rules + quota for EVERYONE, plus a per-sewadar audit trail**. Fixes two production bugs: (1) `check_deployment`/`check_deployment_batch` short-circuited for aso/super_admin, so the ASO could assign past a CENTRE's allocated quota (50 → 53 on Finalize Deployment) and out of a department's restriction rules — now admins keep their DESIGNED exemptions (deadline/done/master-switch/centre-lock) but pass the same eligibility + quota gates as centre roles; (2) no record of who changed what on which sewadar — adds `sewadar_audit_log` + SECURITY DEFINER triggers (`trg_audit_deployment`/`trg_audit_consent`/`trg_audit_lock`) logging MAJOR events only (admin deployment writes, anything touching the final deployed department, admin consent fixes, centre lock/unlock — centre-role routine writes are NOT logged). Quota semantics: a sewadar consumes quota from its **effective** department (`COALESCE(deployed_department_id, department_id)`), evaluated per the ROW's centre root via the new `get_dept_quota_remaining(schedule, dept, centre)` helper (not the caller's center), and multi-row statements are re-checked AFTER the write — `check_deployment_batch` (INSERT, `new_rows` only) and the new `check_deployment_batch_upd` (UPDATE, via `trg_check_deployment_batch_upd`; `OLD TABLE` is only legal on UPDATE/DELETE triggers, so UPDATE got its own function) — raising only on a NET increase past quota (`post > max AND post > pre` from `old_rows`), so a whole chunk can't slip past per-row checks while corrective moves OUT of a legacy over-quota department stay possible. RLS: `sewadar_audit_log` read = aso/super_admin; writes flow through the triggers (function owner bypasses RLS). **Non-destructive; safe to re-run.** Verification queries at the bottom of the file.
17. `sql/v18_audit_log_aso.sql` — **ASO destructive actions get audited too**: v16 (G+) rebuilt `audit_log_insert` around `get_portal_user_role()` but kept it super_admin-only, so every destructive action performed from an **aso** account (delete schedule / delete department / delete allocations / REMOVE_ALL on Schedule Maker) silently wrote no audit row. Widens `audit_log_insert` to `aso` + `super_admin`; reads stay admin-only. The UI treats audit writes as best-effort and now surfaces failures via console.warn (supabase-js returns errors instead of throwing, so the previous try/catch never fired). **Non-destructive; safe to re-run.** Verification queries at the bottom of the file.
18. `sql/v19_vss_creation_gate.sql` — **VSS creation gate + deadline sync**: adds a third master switch `portal_settings.vss_creation_open` (**default CLOSED** — centres cannot create VSS registrations until the ASO opens "Add VSS" in the VSS Dashboard), plus a deadline window helper (`vss_creation_window_open` — true while any open schedule has `deadline IS NULL OR deadline > now()`; NULL deadlines never block). A guard trigger (`trg_a_guard_vss_registration`, named to fire before the temp-ID/age triggers so rejected inserts don't burn sequence numbers) blocks centre-role **INSERT** unless switch + window are both open, and blocks centre-role **UPDATE/DELETE** once the window closes ("deadline over → everything disabled"). aso/super_admin exempt. VSFB immutability was already DB-enforced (v9 RLS: centre roles can't touch `status='assigned'` registrations; v4 keeps roster writes super_admin-only) — this migration adds nothing there. **Non-destructive; safe to re-run.** Verification queries at the bottom of the file.
19. `sql/v20_aso_readonly.sql` — **aso becomes read-only everywhere (phase-2 hardening)**: recreates `sewadar_consents.consent_write` (FOR ALL) and `deployments.deploy_v2_insert/update/delete` with only `super_admin` unrestricted + the unchanged centre-role subtree arms — dropping every aso write grant that v8/v14 had added (supersedes v14; **super_admin is now the sole finalizer**). Reads stay open via `consent_read`/`deploy_v2_read`. Schedules/departments/allocations needed nothing (v16 H1 already removed those grants); `audit_log_insert` (v18) intentionally keeps its aso arm. Frontend counterpart in the same change: Finalize Deployment hides *Enable editing*/​*Save Draft* behind a View-only pill, Consent/VSS dashboards hide switch toggles, AddVssForm goes fully read-only (incl. VSFB assign → super_admin), Consent Dashboard unlock buttons super_admin-only. **Non-destructive; safe to re-run.** Verification queries at the bottom of the file.
20. `sql/v21_centre_control_panel.sql` — **superadmin Control Panel overrides**: adds `centre_overrides` (presence = OPEN; `centre '*'`=ALL / root CENTRE — SC_SPs inherit; `department_id NULL`=all departments else just that one; unique `(schedule_id, centre, COALESCE(department_id, sentinel))`) and `centre_vss_overrides` (tri-state `creation_open`/`deployment_open`, `centre UNIQUE` with `'*'` wildcard; NULL = inherit global switch/window). New SECURITY DEFINER helpers: `is_centre_override_open(schedule, centre, dept?)` — dept-NULL calls match centre-wide rows only (so a department-scoped unlock does NOT reopen consent rows), dept-given calls also match that department's scoped rows; `vss_deploy_open_for_centre`, `centre_vss_creation_override`, `vss_creation_open_for_centre`; client RPC `get_my_effective_gates(schedule)`. Patches the enforcement triggers: `block_after_deadline` (override bypasses lock+switch+deadline, never `done`; resolves the row's department on `deployments` so a dept-scoped unlock survives this earlier-firing gate), `check_deployment` (same bypass + the consent-given check relaxes under an override — consent Yes or No may be deployed while they hold no final department), both batch re-checks, `check_centre_lock` (a centre under an override may lock despite closed switch/past deadline — incharge compulsion intact), `block_locked_delete` (unfinalized cleanup allowed under an open override), `check_department_incharge` (dept-scoped unlock permits that dept's incharge edits), `guard_vss_registration_write` (tri-state creation override wins over switch∧window). Quota + restriction rules are untouched by design; ASO-finalized sewadars stay frozen via v15/v16 regardless of any override. Bootstraps the v19 switch/window helpers (column + functions) at the top so drifted DBs that skipped v19 don't abort mid-file. RLS: reads aso/super_admin, writes super_admin only. **Non-destructive; safe to re-run.** Verification queries at the bottom of the file.
21. `sql/v32_freeze_deployed_sewadars.sql` — **deployed-sewadar freeze (v32)**: centre roles can no longer UPDATE/DELETE a deployed regular sewadar's `deployments` row or its `sewadar_consents` row — the freeze applies **BEFORE any centre lock or deadline** (`deployments.department_id` is NOT NULL, so any existing row = deployed). Two re-runnable triggers, `trg_a_freeze_deployed_deploy` (`deployments` BEFORE UPDATE OR DELETE) and `trg_a_freeze_consent_of_deployed` (`sewadar_consents` BEFORE UPDATE OR DELETE), call the SECURITY DEFINER `freeze_deployed_rows()` (TG_TABLE_NAME switch, `search_path=''`). Exempt: aso/super_admin; a **normal** `is_centre_override_open(...)` — called with the ROW's department for `deployments` and `NULL::uuid` (centre-wide only) for consents; VSS badges (ILIKE `'VS%'` or present in `vss_sewadars`). **Undeployed-only override rows never bypass**; brand-new deployments (INSERT) stay allowed; ASO-finalized rows were already frozen via v15/v16. SQL-editor runs (no portal role → treated as centre role) can use `ALTER TABLE ... DISABLE TRIGGER` as an escape hatch (documented in the header). **Non-destructive; safe to re-run.** Verification queries at the bottom of the file.

23. `sql/v34_vss_override_force_open.sql` — **VSS is gated SOLELY by its effective switch; lock + deadline do NOT bind VSS**. This is v30's stated intent, never fully implemented: v30 made `block_after_deadline()` VSS-aware but only under an explicit per-centre tri-state "Open" row, and `check_deployment()`, the `check_deployment_batch()` / `check_deployment_batch_upd()` AFTER-statement gates, and `block_locked_delete()` only honoured GENERIC `centre_overrides` — so on a LOCKED centre with a PASSED deadline, flipping the global `vss_deployment_open` switch (the Control Panel "VSS Deployment" master switch) did NOT reopen VSS deployment (writes died with *"Deployment is locked by this centre"* / *"Deadline has passed"*). This migration makes ALL four gates key off `vss_deploy_open_for_centre(centre)` (the effective VSS switch: `global && COALESCE(override, true)`): switch ON ⇒ VSS consent + deployment fully open for the centre past lock + deadline; switch OFF ⇒ *"VSS deployment is closed"* (v31 hard global: a per-centre Open knob cannot reopen it; a per-centre Closed knob force-closes). `status='done'` stays terminal, quotas + restriction rules always bind, ASO-finalized rows stay frozen (v15/v16), and generic `centre_overrides` never reopen VSS. New helper `vss_deployment_force_open(centre)` (specific-centre row wins over `'*'`) is informational only; `get_my_effective_gates` now returns `vss_deployment_force_open` alongside `vss_deployment_open` so the VSS page shows the green "open / specially opened for your centre" banner and gates the UI on `vssOpen: masterOpen` (`VssPage.jsx`) — matching the DB. **Post-v37:** the operator honors this effective VSS switch for VSS-population rows (fail-closed); regular rows keep the bypass. **Non-destructive; safe to re-run.** Run AFTER v30 + v31 (supersedes the earlier force-open-only draft of this file — re-run to upgrade in place).
24. `sql/v35_exclude_aso_from_quota.sql` — **AREA SECRETARY OFFICE-home sewadars excluded from quota counts**, client + server. Sewadars whose home centre is AREA SECRETARY OFFICE no longer consume department quota in the quota math (`src/lib/logic.js`) or the DB trigger (`check_deployment` / batch re-checks). **Non-destructive; safe to re-run.**
25. `sql/v36_vss_operator.sql` — **reusable `vss_operator` role** (a value in `portal_users.role`, no hardcoded email/name): all-centre read (consents, deployments, sewadars, `vss_sewadars`, `vss_registrations`); scoped all-centre write (consent rows, INSERT-only deployments with requested `department_id`, VSS create + VSFB assign via `assign_vss_registration`); bypasses deadline/lock/switches like super_admin; never `deployed_department_id`, Finalize, Control Panel, Schedule, overrides, users, or audit; bound by `done`, quota, restriction/VSS rules, ELDERLY, phantom-badge rejection, v15/v16 finalized rows, and the v32 DEPLOYED freeze. **Non-destructive; safe to re-run.** Run after v34 + v35.  28. `sql/v39_attendance_analytics.sql` (mirror `supabase/migrations/0042_v39_attendance_analytics.sql`) — **attendance analytics, read-only**. Adds the composite index `idx_dp_attendance_sessions(schedule_id, in_date, centre)` and **five SECURITY DEFINER RPCs that resolve the CALLER'S OWN SCOPE INSIDE the function**: `attendance_scope_centres(schedule)`, `attendance_allowed_depts(schedule)`, `attendance_daily_summary(schedule, date)`, `attendance_sewadar_summary(schedule)`, `attendance_scanner_ops(schedule, date)`. Scope: aso/super_admin → all centres; centre_user/centre_admin → `get_my_subtree_centres()`; dept_incharge → own centre narrowed to `get_my_dept_ids(schedule)`; **every other role (incl. `scanner`, `vss_operator`, and SQL-editor runs with no portal role) returns ZERO rows — fail closed**. `days_present` counts DISTINCT `in_date`, so an IN/OUT pair on one day counts once. **Deliberately NOT in scope:** no new RLS policy, no grants, no write path — `scan_in`/`scan_out` remain the only writers, and quota/rules/locks/deadlines/the v32 freeze are all untouched. **The RPCs query `public.dp_attendance_sessions` directly and never call `get_open_session()`** — see the open bug note below. **Non-destructive; safe to re-run.** Run AFTER v38c. Verification queries at the bottom of the file (the scope check is the important one: log in as each role and confirm the row counts differ).

> **BUG FIXED 2026-09-27 (was "OPEN BUG").** `sql/v28_rename_shared_tables.sql` lines 481–490 redefined `get_open_session()` with a statement that could not parse, so the redefinition **never took effect** and v26's version silently survived. Two separate defects, not one: (1) `DROP FUNCTION IF EXISTS public.get_open_session(p_badge text, p_schedule uuid)` named its arguments by **parameter name**, which Postgres does not allow there — it requires argument **types**, i.e. `(text, uuid)` (see the correct form at v26:83); and (2) the statement had **no terminating semicolon** and the `CREATE OR REPLACE FUNCTION` keyword was **missing entirely**, leaving a bare `RETURNS ...`. The surviving v26 function worked only by accident, resolving `public.attendance_sessions` through the v28 compatibility view. **Both source copies** (`sql/v28…` and `supabase/migrations/0029_v28…`, which CI holds byte-identical) are now repaired, and `v40` independently redefines the function to read `public.dp_attendance_sessions` directly, which removes the dependency on the compat view altogether.

 29. `sql/v40_attendance_venue_scope.sql` (mirror `supabase/migrations/0043_v40_attendance_venue_scope.sql`) — **attendance venue + home-centre scope. Run AFTER v39; before it, the Daily tab reports 0% attendance for everyone and both scanning pages render blank.** Attendance is scanned at a single physical venue (**"Bhati - Delhi MC"**, defined once in `public.attendance_venue()`), and because "anyone may scan for anyone", `attendance_sessions.centre` was being asked to do three incompatible jobs: record the venue, act as the RLS access key, **and** serve as the reporting axis. The consequence was silent and total — v39's `attendance_daily_summary` grouped expectations by the sewadar's home centre (`deployments.centre`) but presence by the venue (`attendance_sessions.centre`), then joined them `ON p.centre = agg.centre`. With one constant venue those never match, so `present` was always `0` and **every centre, every day, read as fully absent** — correctly-shaped rows carrying entirely wrong numbers, which is why scope testing alone never caught it. Separately `att_read`/`att_update` gated on `centre = get_portal_user_centre()`, so a dept_incharge at `SECTOR-15-A` matched **zero** rows (every row's centre was the venue) and `ScannerPage`/`DeptInchargePage` — which read the table directly — showed nothing; the policy also compared a single centre name, so it could never have matched an SC_SP's sewadars for a root CENTRE user anyway. **The fix splits the three jobs across three columns the schema already had:** `centre` = the venue (informational only, never a scope or reporting key), `sewadar_centre` = the sewadar's home centre → scope + reporting, `in_scanner_centre` = the operator's own centre → accountability. `scan_in` now records the venue in `centre` and the operator's centre in `in_scanner_centre`; the anti-spoofing centre pin (v26:140-142) is **removed**, since `centre` no longer carries privilege and open scanning is a requirement (`p_centre` is retained in the signature for caller compatibility and deliberately ignored). `att_read`/`att_update` now scope on `sewadar_centre = ANY(get_my_subtree_centres())` — so sub-tree SC_SPs finally resolve — **or** the caller's own scans, so a scanner keeps the "last N scans I did" list and the forgot-OUT recovery even for a sewadar from another centre. The new `attendance_sewadar_centre_visible()` **fails closed**: only `centre_user`/`centre_admin`/`dept_incharge`/`scanner` get visibility, so `vss_operator` and any future role are denied. Adds the matching index `idx_dp_att_schedule_homecentre(schedule_id, in_date, sewadar_centre)`. **Untouched:** the scan authorisation ladder (`scanner`/`dept_incharge`/`aso`/`super_admin` only — unchanged, and `att_insert` stays role-only with no centre condition, which is what makes open scanning true), quota, restriction rules, locks, deadlines, master switches, the v32 deployed-freeze, and v15/v16 finalized rows. **Non-destructive; safe to re-run.**
 30. **v39 corrections shipped in the same change (v39 is a NEW file, never applied to production, so these are fixes-before-shipping rather than a new migration):** (a) `attendance_daily_summary` now filters, groups and joins on `a.sewadar_centre` instead of `a.centre` — **this is the bug above**; aso/super_admin bypass the centre predicate so sewadars whose home centre could not be resolved (`sewadar_centre IS NULL`) still appear for them.  32. `sql/v42_get_open_session_null.sql` (mirror `supabase/migrations/0045_v42_get_open_session_null.sql`) — **`get_open_session` returns real NULL, not an all-NULL row. The function is declared `RETURNS public.dp_attendance_sessions` (a table row type) and written `SELECT * INTO v_row … LIMIT 1; RETURN v_row;`. On a miss, plpgsql assigns an **all-NULL record** to `v_row` and returns it. That record compares equal to SQL NULL under `IS NULL`, but PostgREST never asks that — it JSON-serialises the composite, and an all-NULL record serialises to a **truthy object**: `{"id": null, "status": null, "in_date": null, "in_time": null, "schedule_id": null, "badge_number": null}` (verified on PG 15 via `to_jsonb`).
